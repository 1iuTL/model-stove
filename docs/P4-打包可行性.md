## 一、结论

**成功。** 在 Windows 10.0.26200 / Node 24.22.0 / npm 11.19.1 下：

- `npm install -D electron-builder` 直连 `https://registry.npmjs.org/` 成功
  （新增 271 个包，耗时 59s，exit 0）；
- `electron-builder 26.15.3` 复用 `node_modules/electron/dist`（Electron
  43.8.0）产出 `dist/win-unpacked/`，exit 0；
- 可执行文件 `dist/win-unpacked/Model Stove.exe` 存在（228.5 MiB），
  `resources/app.asar` 存在（567,117 字节），asar 内含
  `src/main.js`、`context-proxy.mjs`、`ui-inject.mjs` 等预期文件；
- 构建过程**没有下载 Electron**，也没有下载 winCodeSign/rcedit/NSIS
  等 electron-builder 二进制（日志中无任何 URL/下载行）；
- `npm test` 仍为 **393 项全绿**，`node tools/test_shell_load.mjs` 全绿。

**但这只是“能打包”，不等于“能直接运行”**：代理脚本在 asar 内的路径和
外部 Node.js 依赖尚未改造，真实进程也未在本环境启动（见第七节）。

## 七、已知限制（本轮未解决）

1. **asar 内路径与外置 Node 的冲突（最关键）**：`src/main.js` 里
   `REPO_ROOT = path.join(__dirname, '..')`，打包后是
   `resources\app.asar`；代理脚本路径是
   `resources\app.asar\context-proxy.mjs`，而启动代理用的是
   `spawn(nodeExe, [PROXY_SCRIPT], { cwd: REPO_ROOT })`。
   - 外部 `node.exe` 不能执行 asar 内的文件，`cwd` 也指向一个文件而非目录；
     真实启动代理时会失败（本轮没有启动进程，未取得运行期报错）；
   - `context-proxy.mjs` 还静态 `import './ui-inject.mjs'`，两者必须一起
     解包/放到真实目录；
   - 解决方向：`asarUnpack: ["context-proxy.mjs", "ui-inject.mjs"]`（或
     `extraResources`），并在运行时把路径映射到 `app.asar.unpacked`，
     再做真实进程验证。
2. **仍依赖系统 Node.js**：`findNodeExe()` 找不到 node 时会给
   “没找到 node.exe”的提示；本包没有携带 Node 运行时。正式分发要么要求
   用户安装 Node，要么把 `node.exe` 作为 `extraResources` 一起带上并调整
   `findNodeExe()`。
3. **`tools/allow-lan.ps1` 未打进包**：`files` 白名单没有 `tools/**`，
   但主进程在开 LAN 时引用 `REPO_ROOT/tools/allow-lan.ps1`；打包后该功能
   会因缺脚本失败。后续需把它加入 `extraResources` 或 `files`。
4. **防火墙规则展示路径过期**：`FW_RULES` 中 app 的 program 指向
   `REPO_ROOT/node_modules/electron/dist/electron.exe`，打包后该路径不存在，
   防火墙状态/规则检查会显示旧路径（不影响打包本身）。
5. **未签名、未改图标/版本资源**：exe 的 VersionInfo 仍是
   `FileDescription=Electron`、`ProductName=Electron`、
   `OriginalFilename=electron.exe`，图标也是 Electron 默认图标（因为
   `signAndEditExecutable: false`）。直接分发会触发 SmartScreen 提示。
6. **没有真实启动验证**：受 DSH 命名管道限制，Electron 在本环境启动即崩
   （见 `docs/P4-进度.md` 第九节），因此 asar 路径、托盘、代理、llama-server
   联动都未做运行期验证。
7. **`author` 缺失**：electron-builder 有警告；做 NSIS/Inno 前建议补上，
   同时补齐 `appId` / `productName` / 图标等元数据。
8. **未做安装器/签名/发布**：`dist/` 只有 `win-unpacked` 和
   `builder-debug.yml`，没有 `.exe` 安装器。

## 八、后续建议（只列前置，不决策 NSIS vs Inno）

共同前置（无论选哪种安装器）：

- 先修第七节第 1、2 条：把 `context-proxy.mjs` / `ui-inject.mjs` 解包到
  `app.asar.unpacked` 并改路径解析；决定 Node 运行时是“要求系统安装”还是
  “随包携带”；
- 把 `tools/allow-lan.ps1` 作为资源打进包；
- 补 `package.json` 的 `author`，准备 `model-stove.ico` 作为 `win.icon`；
- 在真实 Windows 桌面环境跑一遍 `win-unpacked\Model Stove.exe`，验证代理、
  llama-server、托盘和关窗保活；
- 若需签名，准备代码签名证书与时间戳服务；不签名则应接受 SmartScreen 警告。

NSIS（electron-builder 内置 target）额外前置：

- 目标改为 `nsis`，需要 electron-builder 下载 `nsis` / `nsis-resources`
  二进制；继续用 `ELECTRON_BUILDER_BINARIES_MIRROR` 并确认镜像可访问；
- 若同时要改 exe 图标/元数据或签名，会触发 winCodeSign/rcedit 下载
  （`signAndEditExecutable` 不能像本轮一样关闭；可评估
  `signExecutable: false` 保留资源编辑、跳过签名）；
- 需要定 installMode（per-user / per-machine）、安装目录、快捷方式、
  卸载项、安装包图标、artifactName 等；中文安装界面需确认 NSIS 语言包。

Inno Setup（不是 electron-builder 的 target）额外前置：

- 需单独安装 Inno Setup 6（`ISCC.exe`）并维护 `.iss` 脚本，以
  `dist/win-unpacked` 作为 `[Files]` 源；
- 需要定义 AppId/AppName/AppVersion/DefaultDirName/PrivilegesRequired、
  开始菜单/桌面快捷方式、卸载项、中文语言文件（ChineseSimplified.isl）；
- 若签名，需要 `signtool` + 证书；自动更新/发布链路也要另行考虑
  （electron-builder 的 publish 不直接覆盖 Inno）；
- 安装器工具链与 electron-builder 解耦，构建时间/维护成本更高，但安装
  界面和自定义步骤更灵活。

网络侧：本次 npm 直连可用；dir 构建没有触碰 electron-builder 二进制镜像。
后续 NSIS/winCodeSign 下载必须实测镜像 URL；Inno Setup 安装包来源
（jrsoftware）本轮未测试。
