## 二、威胁模型与取舍

### 2.1 防线边界

- **主要对手是同一局域网里的其他设备**：能访问代理端口、能反复猜 6 位码，
  但读不到本机文件系统。
- 纵深顺序：默认回环（P0）→ LAN 必须 API Key（P0/P1）→ 设备 key（本阶段）
  → 配对码（本阶段）→ 限流 + 审计（本阶段）。
- **设备 key 不是 API Key 的替代**：LAN 模式仍应保留 `--api-key`（或
  `--api-key-file`）作为上游最后一道锁；设备 key 解决的是"每个设备单独撤销"
  与"配对后不用手抄 API Key"。
- **能读本机文件系统的攻击者不在防线内**：设备 key 的 sha256 不能反推
  256 bit 明文；但 6 位配对码只有约 20 bit，离线爆破 1e6 次哈希很容易。
  配对码的边界是 TTL + 尝试上限 + 上游限流，不是哈希本身。
- 本阶段不做 TLS；局域网明文传输时设备 key 仍可能被同网段嗅探，TLS/隧道
  属于 P3/P4。

### 2.2 落盘内容

设备注册表（默认与配对同文件）：

```json
{
  "version": 1,
  "devices": [
    {
      "id": "dev_1a2b3c4d",
      "name": "手机",
      "prefix": "9f86d081",
      "hash": "<sha256(key) 的 64 位 hex>",
      "createdAt": 1700000000000,
      "lastUsedAt": 1700000000000,
      "revokedAt": null,
      "expiresAt": null,
      "rotatedAt": null,
      "lastIp": "192.168.1.20"
    }
  ],
  "pairing": [
    {
      "id": "pair_5e6f7a8b",
      "hash": "<sha256(salt + ':' + code) 的 64 位 hex>",
      "salt": "<16 字节 hex>",
      "createdAt": 1700000000000,
      "expiresAt": 1700000300000,
      "attempts": 0,
      "lastAttemptAt": null
    }
  ]
}
```

- **没有明文 key / 明文 code**；`prefix` 只是前 8 个字符，用于界面辨认，
  不参与验证。
- 设备 key：32 字节 `crypto.randomBytes(32)` → 64 位 hex（256 bit 熵）。
- 配对码：`crypto.randomInt(0, 1000000)` → 6 位十进制（含前导零），
  存 `sha256(salt + ':' + code)`。salt 每个码随机 16 字节。
- 文件权限 `0o600` 是尽力而为；Windows 上最终以 ACL 为准。

### 2.3 配对尝试次数的取舍（重要）

`redeem(code)` 只有 code 一个输入，服务端**无法知道一个错误码本来想兑换
哪一条配对**。因此实现为：

- 6 位格式的错码 → 当前**所有活动配对**的 `attempts` 各 +1；
- 某条达到 `maxAttempts`（默认 5）→ 立即从文件删除（作废）；
- 格式非法的输入（空、长度不对、非数字）→ `malformed`，不消耗次数；
- 过期码 → `expired`，顺手清掉；没有活动码 → `no-pairing`；
- 正确的码在成功时先删除再签发设备，保证单次使用（中途崩溃最多重新配对）。

取舍：错码会消耗所有待配对码的额度，攻击者可以在 5 次内把代码"打死"
（DoS，需要用户重新生成）；但反过来，如果只按码记录，就根本追不到错码，
等于允许在 5 分钟内无限猜。通常同一时间只有一条待配对码，配合上游限流
（按 IP）后，这个取舍比"无限猜"安全。多设备同时配对是少数场景。

### 2.4 常量时间比较

`verifyKey` 先对输入做格式校验、sha256，然后对**全部设备**逐条
`crypto.timingSafeEqual`（64 字节），不因命中位置提前返回；比较次数只与
设备数量有关。吊销/过期状态在比较之后判断，返回 `revoked` / `expired`
只是告诉持有者"这个 key 曾经有效"，不泄露 key 本身。

### 2.5 审计日志

- JSONL，一行一个对象，字段 `ts/event/deviceId?/ip?/detail?`；
- `detail` 只应放设备名、模型 id、错误码、路由等短文本。**绝不能**放
  提示词、补全内容、请求头、API Key 或请求体；调用方责任，模块只能做
  500 字符截断和 JSON 转义；
- 写前检查"当前大小 + 新行 > `maxBytes`"就轮转；`keepFiles=2` 表示保留
  `<file>.1`、`<file>.2` 两个历史文件，更旧的丢弃；
- `read()` 跨当前文件与轮转文件读最近 N 条（默认 200），按时间从旧到新，
  坏行/非对象行跳过；
- 追加不做 fsync，硬断电可能丢最后一行；轮转是多次 rename，不是跨文件
  原子事务，极端崩溃时可能留下空档。审计是"运行事实记录"，不是不可篡改
  账本：本机攻击者可以改/删它。

### 2.6 限流器

- 每个 key 一个令牌桶：初值 `capacity`，按 `refillPerSec` 连续补充；
- `take` 消费 1 个；`retryAfterMs` 不消费，只估算还差多少毫秒；
- `Map` 插入顺序当 LRU：`take` 和 `retryAfterMs` 都算访问，超过 `maxKeys`
  从队首删最久未访问的 key；
- key 超过 256 字符截断；null/空 key 直接拒绝，不占内存；
- **已知绕过**：攻击者用大量伪造 key 可以把旧桶挤出内存，从而让按 key
  的限流失效。接线时 key 取稳定身份（如 `${ip}|${route}`），并另设全局/
  连接级上限；内存上限与精确限流不可兼得。
- 限流状态只在内存，进程重启清零；用注入的 `now` 可测试补充速率。

### 2.7 并发假设

注册表/配对文件假定**单进程单写者**（本应用只有一个外壳进程）。没有文件锁；
两个外壳同时写会以最后一次 rename 为准，互相覆盖。`verifyKey` 的
`lastUsedAt` 写盘节流为同设备 60 秒一次，降低热路径 IO。

const security = require('./src/core/security');

### 3.1 设备注册表

```js
const registry = security.createDeviceRegistry({
  file,           // 必填：注册表 JSON 完整路径
  fs,             // 可选：默认 node:fs，测试可注入
  now,            // 可选：默认 Date.now
  crypto,         // 可选：默认 node:crypto
});

registry.issueDevice({ name, ttlMs? })
// -> { id: 'dev_xxxxxxxx', key: '<64 hex>', name, createdAt }
// ttlMs 只影响内部 expiresAt；明文 key 只在此出现一次，不写盘、不应写日志。

registry.verifyKey(key, { ip? })
// -> { ok: true,  device: { id, name, prefix, createdAt, lastUsedAt, revokedAt }, reason: 'ok' }
// -> { ok: false, reason: 'missing' | 'invalid' | 'revoked' | 'expired' }
// 命中后 lastUsedAt 每 60 秒最多落盘一次；ip 只记在内部 lastIp，不在列表暴露。

registry.revokeDevice(id)
// -> { ok: true, device }（已吊销时额外 alreadyRevoked: true）
// -> { ok: false, reason: 'not-found' }

registry.rotateKey(id)
// -> { id, key, name, createdAt }（新 key，旧 key 的 hash 立即被覆盖）
// -> { ok: false, reason: 'not-found' | 'revoked' | 'expired' }
// 不延长原 expiresAt；已过期设备拒绝轮换，调用方应重新 issue。

registry.listDevices()
// -> [{ id, name, prefix, createdAt, lastUsedAt, revokedAt }]，按签发顺序

registry.readPairing() / registry.writePairing(entries)
// 供 createPairingService 同文件模式使用；一般不要直接调用。
```

参数校验：`file` 缺失/非字符串抛 `TypeError`。

### 3.2 配对码

```js
const pairing = security.createPairingService({
  registry,       // 必填：createDeviceRegistry() 的返回值
  file,           // 可选：独立配对文件；省略 = 与注册表同文件（推荐）
  now,            // 可选
  crypto,         // 可选
  ttlMs,          // 可选，默认 5 * 60 * 1000
  maxAttempts,    // 可选，默认 5
});

pairing.createPairing()
// -> { code: '012345', expiresAt }（code 只出现这一次）

pairing.redeem(code, { name, ip? })
// -> { ok: true, device: { id, key, name, createdAt }, reason: 'ok' }
// -> { ok: false, reason: 'malformed' | 'no-pairing' | 'expired'
//                        | 'invalid-code' | 'max-attempts' }
// 成功 = 删除配对码 + registry.issueDevice()；设备 key 明文只返回一次。

pairing.pruneExpired()
// -> 删除的条数（过期或 attempts >= maxAttempts）
```

- **同文件模式（默认/推荐）**：一次配对要"删码 + 发 key"，与注册表共用同一个
  状态快照，少一个需要备份/校验的文件；设备与配对一起原子写。
- **独立文件模式**：文件格式为 `{ "version": 1, "pairing": [...] }`。若传入的
  `file` 与注册表路径相同会抛 `TypeError`（否则会覆盖 `devices`）。
- 独立文件的坏文件同样备份成 `*.bad-<ISO>` 后从空状态继续；最近一次备份路径
  通过 `pairing.backupFile` 读取。

### 3.3 审计日志

```js
const audit = security.createAuditLog({
  file,           // 必填
  fs, now,
  maxBytes,       // 可选，默认 5 * 1024 * 1024
  keepFiles,      // 可选，默认 2；0 = 不保留历史
});

audit.append({ event, deviceId?, ip?, detail? })
// -> 写入的条目 { ts, event, deviceId?, ip?, detail? }
// event 为空/非字符串抛 TypeError；detail 截断到 500 字符；
// deviceId/ip/event 各截断到 64 字符。

audit.read({ limit = 200 })
// -> 最近 limit 条，按时间从旧到新；跨 .1/.2 轮转文件；坏行跳过。
```

事件常量：

```js
security.AUDIT_EVENTS = {
  AUTH_OK: 'auth_ok',
  AUTH_FAIL: 'auth_fail',
  PAIR_CREATE: 'pair_create',
  PAIR_REDEEM_FAIL: 'pair_redeem_fail',
  PAIR_REDEEM_OK: 'pair_redeem_ok',
  REVOKE: 'revoke',
  RATE_LIMITED: 'rate_limited',
};
```

### 3.4 限流器

```js
const limiter = security.createRateLimiter({
  capacity,       // 可选，默认 20（正整数）
  refillPerSec,   // 可选，默认 1（正数，支持小数）
  maxKeys,        // 可选，默认 1024（正整数）
  now,            // 可选，默认 Date.now
});

limiter.take(key)          // -> true 允许 / false 拒绝（不抛错）
limiter.retryAfterMs(key)  // -> 0 或还需等待的毫秒数（新 key 视为满桶）
limiter.forget(key)        // -> true 表示确实删掉了
limiter.size()             // -> 当前桶数量（测试/观测用）
```

## 六、给 Lead 的接线建议（本阶段刻意未做）

1. **初始化位置**：在 `initRuntime()` 里 `paths`/`ensureDirs` 之后创建，
   文件路径全部来自 `paths`，不要写死用户目录：
   ```js
   const security = require('./core/security');
   const registry = security.createDeviceRegistry({
     file: path.join(paths.dataDir, 'security', 'devices.json'),
   });
   const pairing = security.createPairingService({ registry });
   const audit = security.createAuditLog({
     file: path.join(paths.logsDir, 'security-audit.jsonl'),
   });
   const limiter = security.createRateLimiter({ capacity: 20, refillPerSec: 1 });
   ```
   `security/` 目录由 `atomicWriteJson` 自动创建；`ensureDirs` 不用改。
2. **请求链顺序**：回环/LAN 绑定检查（P0）→ 限流 `take(`${ip}|auth`)` →
   设备 key 验证（`Authorization: Bearer`）或既有 API Key → 业务。
   失败统一 401；限流拒绝返回 429 + `Retry-After`（由 `retryAfterMs` 换算）。
   `verifyKey` 是 sha256 + 常数时间比较，成本很低，不必做请求级缓存。
3. **配对走本地 IPC**：`security:pairCreate` 只允许本机渲染进程触发，返回
   `{ code, expiresAt }` 后界面显示一次；**不要**把 code 写 shell 日志。
   手机端兑换走代理上的受保护端点（当前 API Key/session token 保护），
   成功后设备 key 只回给手机；`security:devices:list/revoke/rotate` 同样
   只走 IPC。启动时调用一次 `pruneExpired()`，可再加低频定时器。
4. **LAN 与 API Key 不变**：设备 key 是追加凭据，不是删除 `--api-key` 的理由；
   `--api-key-file` 优先级仍按既有决策。默认回环也不变。
5. **审计调用点**：`auth_ok`（成功）、`auth_fail`（失败，detail 用 reason）、
   `pair_create`、`pair_redeem_ok`、`pair_redeem_fail`、`revoke`、
   `rate_limited`。`detail` 只放静态原因/设备名/路由；**绝不要**把
   `device.key`、请求头或对话内容传进去。append 失败建议 catch 后写外壳
   日志，不要因为审计盘满而拒绝已通过验证的请求。
6. **两个限流器**：建议认证/配对一个（如 `capacity:5, refillPerSec:0.2`），
   普通请求一个（`20, 1`）。key 用稳定身份 `${ip}|${route}`；配对成功后
   可 `forget(`${ip}|pair`)` 清掉该 IP 的失败计数（若按此设计）。
7. **设备 TTL**：`createPairingService` 目前签发**不过期**设备；若产品需要
   "配对设备 30 天过期"，在 `issueDevice` 调用处传 `ttlMs`，并注意
   `listDevices` 目前不返回 `expiresAt`（见未解决点）。
8. **坏文件告警**：`registry.warnings` / `registry.backupFile`、
   `pairing.backupFile` 可在启动时写一条外壳日志，提醒用户 key 被重置。
9. **后续测试**：接线后补 `tools/test_security_wiring.mjs`（HTTP 401/429、
   配对成功拿 key、吊销后 401），并保持 core 测试纯 Node。

## 七、未解决 / 已知限制

- **未接线**：本阶段只有核心模块与单测，proxy/main/UI 尚未调用；实际
  攻击面要等接线后的集成测试才能验证。
- **配对错码会作废所有活动码**（见 2.3）：是"不可无限猜"的代价，存在
  LAN 内 DoS 窗口；没有按 IP 持久化失败计数，限流器重启即清零。
- **单进程写者**：没有文件锁；两个外壳同时运行会互相覆盖注册表/配对/审计。
- **本地文件读取者**：可看到设备名/前缀/IP/审计内容，可离线爆破 6 位配对码，
  可删改审计；设备 key 本身 256 bit 不可由 hash 反推。没有 at-rest 加密。
- **审计不是防篡改账本**：追加无 fsync、无哈希链、轮转可能丢最旧条目；
  只适合运行诊断与"谁在什么时候认证过"。
- **`listDevices()` 不返回 `expiresAt`**：TTL 在验证时生效，但界面无法显示
  到期时间；接线前若需要展示，建议加字段（本阶段按任务签名保持精确字段）。
- **`rotateKey` 不续期**：保留原 `expiresAt`；已过期设备直接拒绝轮换。
- **限流器内存上限与绕过**：LRU 驱逐会让大量伪造 key 的调用方把旧桶挤掉；
  限流状态不持久化，重启归零。
- **6 位码熵只有 20 bit**：salt 只防预计算，不改变离线可爆破的事实；真正的
  在线保护是 TTL/尝试上限/限流，不要在没有限流的情况下暴露 redeem 端点。
- 没有 TLS；LAN 上设备 key 可能被嗅探（P3/P4）。
- Windows 上 `0o600` 只是尽力而为，实际权限由 ACL 决定。
- 设备/配对条目数量没有硬上限（只有可注入的尝试/大小参数），本地调用方
  可以持续增长文件；接线时若暴露给非本机入口，需要再加配额。
